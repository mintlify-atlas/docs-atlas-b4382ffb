Starting with version 0.30.0, Ratatui was reorganized from a single monolithic crate into a modular Cargo workspace of specialized crates. This split improves compilation times, reduces unnecessary dependencies, provides more stable APIs for third-party widget libraries, and enables `no_std` support in the foundational crate. Most application developers can continue using the top-level `ratatui` crate unchanged — it re-exports everything from the sub-crates for convenience.

## Workspace at a Glance

The Ratatui workspace lives in a single repository at [github.com/ratatui/ratatui](https://github.com/ratatui/ratatui). All crates are currently versioned together for simplicity, though independent versioning may be adopted in the future as APIs stabilize.

## All Crates

### Core Crates

<Accordion title="ratatui — Main crate (v0.30.2)">
  **Purpose:** The single dependency that most applications should declare. Re-exports everything from the other crates and also exposes experimental features.

  **Contents:**
  - Complete widget ecosystem (via `ratatui-widgets`)
  - All terminal backends (via `ratatui-crossterm`, `ratatui-termion`, `ratatui-termwiz`, `ratatui-termina`)
  - Layout system, buffer management, style and color definitions (via `ratatui-core`)
  - Declarative macros (via `ratatui-macros`)

  **Use this when:** You are building a terminal application.

  ```toml
  [dependencies]
  ratatui = "0.30.2"
  ```
</Accordion>

<Accordion title="ratatui-core — Foundation crate (v0.1.2)">
  **Purpose:** Stable, minimal foundation for the entire ecosystem. Designed so that widget library authors can depend on it without being forced to update on every Ratatui release.

  **Contents:**
  - `Widget` and `StatefulWidget` traits
  - `Text`, `Line`, `Span` text types
  - `Buffer` management
  - `Layout` and `Constraint` system
  - `Style`, `Color`, and `Modifier` definitions
  - Symbol collections (braille, borders, block characters)

  **Key property:** Supports `no_std` environments (e.g. embedded systems). The `layout-cache` feature works in `no_std` via `critical-section`.

  **Use this when:** You are authoring a widget library and need a stable, lightweight dependency.

  ```toml
  [dependencies]
  ratatui-core = "0.1.2"
  ```
</Accordion>

<Accordion title="ratatui-widgets — Built-in widgets (v0.3.2)">
  **Purpose:** All standard Ratatui widget implementations.

  **Contents:** Block, Paragraph, List, Table, Chart, BarChart, Gauge, LineGauge, Sparkline, Tabs, Canvas, Scrollbar, Calendar (feature-gated), and more.

  **Use this when:** You are publishing a crate that provides only widgets and want access to the full widget set without pulling in any backend.

  ```toml
  [dependencies]
  ratatui-widgets = "0.3.2"
  ```
</Accordion>

### Backend Crates

Each backend crate depends on `ratatui-core` and provides an implementation of the `Backend` trait for a specific terminal I/O library.

| Crate | Version | Terminal Library | Platforms |
|---|---|---|---|
| `ratatui-crossterm` | 0.1.2 | crossterm 0.29 | Linux, macOS, Windows |
| `ratatui-termion` | 0.1.2 | termion 4 | Linux, macOS (Unix only) |
| `ratatui-termwiz` | 0.1.2 | termwiz 0.23 | Linux, macOS, Windows |
| `ratatui-termina` | 0.1.0 | termina 0.4 | Linux, macOS, Windows |

<Info>
You almost never need to depend on a backend crate directly. Enable the corresponding feature flag on `ratatui` instead (`crossterm`, `termion`, `termwiz`, or `termina`).
</Info>

### Utility Crates

<Accordion title="ratatui-macros — Declarative macros (v0.7.2)">
  **Purpose:** Provides `span!`, `line!`, `text!`, `constraints!`, `constraint!`, `vertical!`, `horizontal!`, and `row!` macros for reducing UI boilerplate.

  Included automatically when you add `ratatui` with the default `macros` feature. Can also be used as a standalone dependency.

  ```toml
  # Standalone usage
  [dependencies]
  ratatui-macros = "0.7.2"
  ```
</Accordion>

## Dependency Diagram

```text
ratatui  (main crate — use this for applications)
├── ratatui-core          (foundational types, no_std compatible)
├── ratatui-widgets   ──► ratatui-core
├── ratatui-crossterm ──► ratatui-core
├── ratatui-termion   ──► ratatui-core
├── ratatui-termwiz   ──► ratatui-core
├── ratatui-termina   ──► ratatui-core
└── ratatui-macros
```

All backend crates depend only on `ratatui-core`, not on `ratatui-widgets`. This means adding a backend never pulls in widget code you don't need.

## Choosing the Right Crate

<CardGroup cols={3}>
  <Card title="Building an app" icon="terminal">
    Use **`ratatui`** with default features. You get everything — backends, widgets, and macros — in one dependency.
  </Card>
  <Card title="Publishing a widget library" icon="puzzle-piece">
    Depend on **`ratatui-core`** only. Your users can pick any `ratatui` version without your library forcing an upgrade.
  </Card>
  <Card title="Only need widgets, no backend" icon="window">
    Use **`ratatui-widgets`**. Useful for rendering to a custom buffer or testing widgets in isolation.
  </Card>
</CardGroup>

## `no_std` Support

`ratatui-core` is compiled with `#![no_std]` and supports embedded and WASM targets. The `std` feature (off by default in `ratatui-core`, on by default in `ratatui`) enables `std::io`-dependent functionality.

```toml
# no_std application — bring in core types only
[dependencies]
ratatui-core = { version = "0.1.2", default-features = false, features = ["layout-cache"] }
```

<Note>
The `layout-cache` feature works in `no_std` environments by using `critical-section` for atomic access. Without it, layout calculations run on every frame and can significantly impact performance on constrained hardware.
</Note>

## Migration from Pre-0.30.0

Before 0.30.0, Ratatui was a single monolithic crate. The split is **fully backward compatible** — all existing code using `ratatui` continues to compile without modification.

### Application Developers

No changes are required. All types are still re-exported from the main `ratatui` crate:

```rust
// This still works exactly as before
use ratatui::{
    widgets::{Block, Paragraph},
    layout::{Layout, Constraint},
    Terminal,
};
```

### Widget Library Authors

If you previously depended on `ratatui` to access `Widget`, `Buffer`, and `Rect`, you can now depend on the lighter `ratatui-core` instead:

```rust
// Before (0.29.x and earlier)
use ratatui::{
    widgets::{Widget, StatefulWidget},
    buffer::Buffer,
    layout::Rect,
};

// After (0.30.0+) — depend on ratatui-core only
use ratatui_core::{
    widgets::{Widget, StatefulWidget},
    buffer::Buffer,
    layout::Rect,
};
```

This reduces the compile-time footprint of your library and decouples your release cadence from the main `ratatui` crate.
